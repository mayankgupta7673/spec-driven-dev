The problem

"Vibe coding" with AI doesn't scale

  • Intent evaporates. A prompt is typed, code appears, the "why" is gone forever.
  • Nothing to review. Reviewers see code with no spec to check it against.
  • Inconsistent output. The same ask yields different results every run.
  • No traceability. You can't link a change back to a requirement or ticket.

Prompt → Code

The gap between a one-line prompt and production code is filled with the model's guesses — not your decisions.

# today
"add an endpoint to submit orders"
# → 200 lines, unknown assumptions
Reality check

AI is not a compiler

“I just see things, say things, run things, and copy-paste things, and it mostly works.”

— Andrej Karpathy, on “vibe coding”

  • Non-deterministic. Precise input does not guarantee perfect output.
  • An assistant, not a compiler. It guesses, and it makes mistakes.
  • You own the output. Review, understand, and test everything it generates.
An analogy

Building a backyard

🔥 “Just build me something cool”

The contractor assumes your intent. The BBQ arrives — but there's no cutout in the stone and no gas line. Every change means tearing up what's already built.

Prompt-and-pray

📐 “The blueprint is the source of truth”

Exact dimensions. Appliances chosen first to define the interface. Utilities laid before pavers. The same blueprint works with any mason.

The idea

Make the specification the source of truth

SDD inserts durable, reviewable artifacts between intent and implementation. The AI agent gets structured context at every step — so results are consistent, auditable, and aligned to the requirement.

Write it down

Every feature begins as a spec.md — what & why, every requirement testable.

Plan the how

A plan turns requirements into architecture, contracts, and a data model.

Execute

Dependency-ordered tasks drive the AI to build a tested vertical slice.

Each phase feeds the next

Artifacts, not vibes

specs/001-order-submission/
├── spec.md # what & why
├── plan.md # how — architecture
├── contracts/
│ └── orders-api.md # request/response
└── tasks.md # ordered checklist
  • Reviewable. Each artifact is a PR-sized, human-readable file.
  • Versioned. The spec evolves in git alongside the code.
  • Structured context. The AI reads the prior artifact instead of guessing.
Fits your backlog

From ticket to merged PR — one id

Requirements originate in JIRA or Azure DevOps. The ticket id becomes the feature id and the single correlation key across the whole journey.

Inbound

A ticket seeds spec.md automatically — never re-typed, always enriched.

Outbound

tasks.md creates child work items linked back under the same ticket.

The demo under the hood

Thin adapters, rich core

  • Triggers ≈ 30 lines. Bind, validate, dispatch, return.
  • Core is Azure-free. Unit tests run offline, no cloud.
  • Swap to Azure = two lines in Program.cs.
See it run

Live: async order submission

# 1 — submit (202 + correlation id)
POST /api/orders
{ "legalEntityId":"ABN-01", "lines":[…] }
→ 202 { "correlationId":"c5d4…" }

# 2 — query status
GET /api/orders/c5d4…/status
→ 200 { "state":"Accepted" }

# 3 — resend same clientRequestId
→ same id · published once (idempotent)
  • 202 + id — caller decoupled from slow writes.
  • Idempotent — safe retries, publish exactly once.
  • Validated — bad input → 400, nothing published.
  • 14 tests green — all offline.
